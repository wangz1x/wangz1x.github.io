你和一个 AI Agent 聊完一轮，点下回车，发生了一件你没察觉的事：这段对话被悄悄记下、提炼、聚合，最终变成"你是什么样的人"这样一份画像，在下次对话时又自动喂回给 Agent。整个过程在后台跑，用户完全无感。

最近我在读 [TencentDB Agent Memory](https://github.com/Tencent/TencentDB-Agent-Memory) 这套记忆系统的源码，把它的核心——从 L0 到 L3 的四层记忆流水线——摸了个遍。这篇文章把这条链拆开：每一层在什么时机触发、吃什么输入、吐什么输出、怎么把下一层接上。

<!--more-->

## 一张图先建立直觉

四层记忆是一条单向提炼链，越往上越抽象、越少：

```
L0 对话（很多条）   →   L1 原子（很多条）   →   L2 场景（≤15个）   →   L3 画像（1个）
原始记录               提炼的事实           聚合的领域          综合的画像
```

每一层都遵循同一个套路：**调度器在合适时机触发 → runner 从上一层读增量 → LLM 处理 → 写到本层存储 → 推进游标 → 触发下一层**。差异只在于"时机怎么定、处理怎么做、存哪"。

## L0：把对话录下来（同步入口）

**L0 是整条链的原料**——原始对话消息，一字不差地存下来。

- **触发时机**：每轮 Agent 答完用户一句话（`agent_end` 事件），立刻触发。不是等会话结束，是**每答完一句就录一次**。
- **输入**：这一轮的对话消息（用户问 + Agent 答 + 中间的工具调用）。
- **输出**：两份存储——
  - `conversations/YYYY-MM-DD.jsonl`（按天分文件、append-only 日志，每行一条消息带租户标签）
  - 向量库的 L0 表（元数据 + 向量 + 全文索引，供语义/关键词检索）
- **关键设计**：录完只做"记录 + 报数"，**不做任何提炼**。它给调度器发个信号"又聊完一轮了"，然后立刻返回——不能让用户等。向量计算这种慢活（2-3 秒）要么扔后台，要么靠服务端嵌入，绝不阻塞用户。

L0 的职责就一句话：**干净增量地把对话存成可检索的真相源**。

## L1：从对话抽出原子记忆（异步沉淀开始）

**L1 是第一层提炼**——把零散对话变成一条条结构化的"原子事实"。

- **触发时机**：由调度器的计数器/idle 定时器决定，**不是 L0 直接触发**。L0 只报数，L1 自己判断"攒够几轮了"或"闲够久了"才跑。这是异步的——L0 录完用户就走了，L1 在后台慢慢抽。
- **输入**：L0 对话（按 `last_l1_cursor` 游标增量查，只处理没抽过的新对话）。
- **输出**：原子记忆——每条带 `type`（persona 个性化 / episodic 事件 / instruction 指令）、`priority`、`scene_name` 的结构化记录。双写到 `records/*.jsonl`（真相源）+ L1 库表（检索引擎）。
- **核心机制**：LLM 抽取（靠提示词指挥产出 JSON）+ **去重**（和已有记忆比对，判定 store/update/merge/skip，防止重复或矛盾）+ 落库（带 embedding，可语义检索）。

L1 产出的不是"这段对话讲了什么"的笼统总结，而是**一条条可独立检索、可去重、带类型的事实**——这是它能被下游聚合的前提。

## L2：把原子聚合成场景（沙箱 LLM 写文件）

**L2 把 L1 的零散原子，聚成"场景叙事"**——比如把"偏好 pnpm""修登录 bug""要求跑 test"这些原子，融进一篇叫"后端开发.md"的连贯叙事。

- **触发时机**：L1 完成后链式推进——`advanceL2Timer` 设个下行定时器（只提前不推后），延迟后触发 L2。
- **输入**：L1 原子记忆 + 现有的场景文件清单。
- **输出**：`scene_blocks/*.md`（每个文件一个场景，人可读的 Markdown 白盒），最多 15 个（可配）。
- **核心机制**：这层和 L1 范式完全不同——**它是个沙箱 LLM agent**。给 LLM 一组文件工具（read/write/edit），工作目录限定在 `scene_blocks/`，LLM 自己读 L1、决定"建新场景 / 更新现有 / 合并相似的"，**直接写 .md 文件**，不靠程序解析 JSON 落盘。

这层的工程细节很考究：LLM 不能真删文件（没有执行权限），只能写个 `[DELETED]` 标记，由程序代删；写前先备份 `scene_blocks/`，写坏了能回滚；场景数到上限就禁止新建，只能合并；提示词里处处是"默认 UPDATE 不是 CREATE""CREATE 前必须先 read 两个最相似的验证"这类踩坑约束。

L2 的产出是**白盒的场景文件**——人能直接 `cat` 看，程序也能读 META 头（created/updated/summary/heat）建索引。场景是 team+agent 粒度的知识库，跨用户共享。

## L3：从场景综合成用户画像（链的终点）

**L3 是最后一层**——从所有场景综合出"这个用户/agent 是谁"的整体画像。

- **触发时机**：L2 完成后 `triggerL3`，但**不是每次都真跑**——要先过 `PersonaTrigger` 的 5 个条件判定：
  1. **P1 显式请求**：LLM 在 L2 时觉得"画像该更新了"，输出 `[PERSONA_UPDATE_REQUEST]` 信号，程序解析后设置标志
  2. **P2 冷启动**：首次提取完成、还没画像、有场景文件
  3. **P2.5 恢复**：画像文件损坏/丢失，重新生成
  4. **P3 首场景**：第一个场景刚建好
  5. **P4 阈值**：攒够 N 条新记忆（每 N 条触发一次）
- **输入**：**变化的 L2 场景**（增量——按 `last_persona_time` 只看上次画像之后更新过的场景，不每次读全部）。
- **输出**：单个 `persona.md`（用户画像，Markdown 白盒）。
- **核心机制**：和 L2 同款"沙箱 LLM 写文件"，LLM 直接写 `persona.md` 的画像正文；程序后处理追加"场景导航"（列出有哪些场景）。L3 全局互斥——同时只跑一个，因为画像是 team+agent 级的，不分会话。

L3 产出的 `persona.md` 就是整条链的终点：所有对话最终浓缩成一篇"用户是什么样的人"。P1 那条特别有意思——**LLM 能在 L2 时主动请求刷新画像**，不靠死阈值，是 LLM 自驱的画像更新。

## 这条链怎么闭环：recall 把记忆喂回去

沉淀链产出的东西，最终在 recall 时用上——每轮对话**前**，自动检索相关记忆注入 prompt：

- **L1 原子**：混合检索（关键词 BM25 + 向量余弦 + RRF 融合），注入到 user prompt 前缀（每轮都变，所以放动态区，不破坏 system prompt 缓存）
- **L3 persona**：读 `persona.md` 画像正文，注入到 system prompt 的 `<user-persona>`（稳定区，可被 Anthropic/OpenAI 的 prompt cache 缓存省 token）
- **L2 场景导航**：注入到 system prompt 的 `<scene-navigation>`（告诉 Agent 有哪些场景维度）

于是闭环成立：**L0 录对话 → L1/L2/L3 沉淀 → recall 注入 → Agent 用记忆答 → 新对话又进 L0**。每轮对话都是这个环的一次循环，记忆边聊边沉淀、边沉淀边用。

## 一个贯穿全链的设计哲学

拆完这四层，你会发现它们共享同一个设计原则：**慢活扔后台、同步入口立刻返回、数据靠游标增量、存储双写（真相源 + 检索引擎）**。

- L0 的向量计算扔后台，`agent_end` 立刻返回，用户不卡
- L1/L2/L3 全是调度器异步触发，不阻塞对话
- 每层都有游标（`last_captured_timestamp` / `last_l1_cursor` / `last_persona_time`），只处理增量
- L0/L1 双写 JSONL（不丢可重建）+ 库表（快查），L2/L3 双写 .md（人可读）+ 索引（程序快查）

这套"分层提炼 + 异步沉淀 + 双写存储 + 白盒可调试"的设计，是这套记忆系统最值得学的地方——它把"让 AI 记住用户"这件听起来很玄的事，拆成了一条清晰、可调试、可追溯的数据流水线。下次你用 Agent 感觉它"记得你"，背后多半就是这条 L0→L3 的链在默默运转。
